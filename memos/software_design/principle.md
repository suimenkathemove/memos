# 設計原則

SOLIDは[solid.md](./solid.md)に分ける。

## KISS(Keep It Simple, Stupid)

いま実装する範囲を、シンプルに作る。

同じ要件を満たすなら、凝った抽象化・技巧的なコード・過剰な設計パターンより、素直で読める形を選ぶ。

違反の例: メール送信だけが要件なのに、テンプレートを独自DSLでパースする仕組みを自作する。

コードは書く時間より読む時間のほうが長い。
凝った作りは、書いた本人以外が読むたびに仕組みの理解を要求し、変更やデバッグのたびにそのための時間がかかる。
自作した仕組みには自作した分のバグとメンテナンスがついてくる。

## YAGNI(You Aren't Gonna Need It)

今要らないものは、作らない。

違反の例: 通知がメールだけなのに「後でSlackやSMSも来るはず」として、NotificationChannelインターフェース + DI + 設定ファイルを用意する。

先回りして用意しても、多くの場合そのまま使われずに終わる。必要になったとしても、その時には要件が想定とずれていて、結局作り直しになる。
しかもそれまでの間、今の要件には必要でないコードを読まないといけなくなる。

## DRY(Don't Repeat Yourself)

「すべての知識は、システム内で単一・明確・信頼できる表現を持たなければならない」

重複を禁じているのは知識であって、コードの見た目ではない。
同じ事実が2箇所に書かれていると、もう片方の存在に気づかず直し漏れて、不整合が起きる。

- 本来のDRY違反
  税率の計算式がサーバとフロントに別々に書かれている。
- DRY違反ではない
  たまたま今は同じ形をしている2つのバリデーション。
  由来する仕様が別なら、片方だけ変わる可能性がある。

判断は「この2つは常に同時に変わるか」。同時に変わらないなら別の知識であり、まとめてはいけない。
これは[solid.md](./solid.md)のSRP(変更を要求するアクターで分ける)と同じ問い。

### 行き過ぎたDRY

形が似ているだけのコードを共通化すると、片方の都合で分岐が増える。
引数のフラグが増え、条件分岐が積み重なり、両方の呼び出し元が共通関数を通じて結合する。
重複より結合のほうが高くつくことが多い。

なので、次の経験則が使われる。

- Rule of Three: 3回目まで待つ
- AHA(Avoid Hasty Abstractions): まず重複させ、知識が同じだと確信できてからまとめる
