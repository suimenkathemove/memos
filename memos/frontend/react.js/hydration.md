# hydration

サーバーが返した静的なHTMLに、クライアント側でReactがイベントハンドラとstateを紐付けて操作可能にする処理。

## 流れ

1. サーバーがHTMLを返す。この時点では表示されるがボタンを押しても反応しない。
2. JSがダウンロードされる。
3. Reactが同じコンポーネントツリーをクライアントで再実行し、既存のDOMと突き合わせる。
4. 一致したDOMにイベントハンドラを付ける。DOMは作り直さない。

## hydration mismatch

3のとき、サーバーの出力とクライアントの出力が食い違うと、hydration mismatchのエラーになる。
Reactは該当箇所のDOMを破棄して作り直すため、表示のちらつきやstateの喪失が起きる。

よくある原因

- `new Date()`, `Math.random()`, `crypto.randomUUID()`など、実行のたびに値が変わるもの。
- `window`, `localStorage`, `navigator`などブラウザAPIをレンダリング中に参照する。
  サーバーでは`undefined`になる。
- サーバーとクライアントでタイムゾーンやロケールが異なる日時フォーマット。
- ブラウザ拡張がHTMLを書き換える。

対処

- クライアントでしか決まらない値は`useEffect`で描画後に設定する。
  初回レンダリングはサーバーと同じ出力にする。
- 日時はサーバーでフォーマットするか、タイムゾーンを固定する。
- どうしても差分が出る要素は`suppressHydrationWarning`を付ける。その要素の1階層のみ有効。
- ブラウザでしか動かないコンポーネントは、SSR自体を外す。
  Next.jsなら`next/dynamic`の`ssr: false`。

## コスト

hydrate対象のコンポーネントが多いほど、3の再実行に時間がかかる。
低スペック端末ほど影響が大きい。

hydrationが終わるまで操作を受け付けないため、TTIのボトルネックになりうる。
ただしReact 18以降はストリーミングと選択的hydrationにより、ツリー全体を待たず、操作された箇所から優先的にhydrateされる。
